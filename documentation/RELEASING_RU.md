# Выпуск и подписи Aurora

## Модель доверия

Локальная 0.14 закрепляет публичный Ed25519-ключ из `src/core/update-trust.json`. GitHub хранит файлы и подписанный манифест, но не закрытый ключ. Обновление проверяет точные URL, версию, платформу, размер и SHA-256, назначение подписи, срок действия и возрастающий номер последовательности. Журнал доверия находится в пользовательском профиле `updates/trust-state.json`; его удаление сбрасывает локально запомненную последовательность.

Это подпись содержимого обновления, не Authenticode или антивирусная проверка. Первую 0.14 следует установить из проверенного источника вручную: предыдущие версии не закрепляли этот ключ. Переход с них не создаёт независимое доверие задним числом.

## Подготовка без публикации

1. Установить зависимости `npm ci` и `npm ci --prefix cloud`; запускать инструменты ключа под Windows-пользователем, создавшим ключ.
2. `npm run release:key -- status` проверяет доступность ключа, выводит только открытый идентификатор. Не запускать `init` ради замены существующего корневого ключа.
3. Собрать и проверить Windows; Linux собирать на Linux и тестировать отдельно. Перед подписью Authenticode (если используется) должен уже быть применён: последующее изменение EXE изменит хеш.
4. Собрать окончательные файлы в отдельную папку с именами `Aurora-0.14.0-Windows-x64.exe`, `Aurora-0.14.0-Linux-x86_64.AppImage`, `Aurora-0.14.0-Linux-x64.pacman`. В манифест входят только реально существующие платформы.
5. `npm run release:sign -- 0.14.0 1 "C:\путь\к\папке-выпуска"` создаёт `Aurora-update.json` и `SHA256SUMS.txt`. Для последующих выпусков номер последовательности должен быть строго больше всех ранее опубликованных, а версия — выше предыдущей. Номер глобальный для всех платформ. Не подписывать параллельно два разных выпуска одним номером. Локальный кандидат с номером 1 ещё не является публикацией.
6. Инструмент не загружает файлы. После проверки и разрешения владельца публикуется единый выпуск `v0.14.0` со всеми подписанными файлами, манифестом и суммами. Не менять файлы уже принятой последовательности. При изменениях выпускать новую версию и последовательность.
7. Проверить скачивание и обновление с отдельного тестового профиля после публикации. Не отдавать старым клиентам неподписанный fallback. Истёкший манифест (180 дней) не принимается: нужен новый более высокий выпуск.

## Резервирование и восстановление

`npm run release:key -- backup "E:\Aurora-release-key.encrypted.pem"` запрашивает скрытый пароль дважды и пишет зашифрованный PKCS8 AES-256-CBC; файл не перезаписывается. Хранить вне проекта и Git, пароль отдельно. Не вводить пароль аргументом команды или в чат.

На отдельной доверенной машине с проверенными исходниками, тем же открытым ключом и зависимостями: `npm run release:key -- restore "E:\Aurora-release-key.encrypted.pem"`, затем `npm run release:key -- status`. Системное хранилище другого пользователя само по себе не переносится. На Linux для инструментов ключа требуется работающий сервис секретов; этот сценарий ещё не проверен на Arch.

## Ротация рабочего ключа

`npm run release:key -- rotate "C:\закрытая-папка\aurora-delegation.json"` создаёт новый закрытый рабочий ключ в системном хранилище и открытый сертификат, подписанный корневым ключом, сроком 180 дней. Сохрани показанный идентификатор и резервируй новый ключ отдельно, установив переменную `AURORA_RELEASE_KEY_ID` с этим публичным идентификатором.

Для выпуска рабочим ключом установи `AURORA_RELEASE_KEY_ID` и передай четвёртым аргументом `release:sign` файл сертификата. Сертификат включится в манифест. Клиент принимает только одноуровневое действующее делегирование корневым ключом для stable-обновлений Aurora. Ротация не отзывает автоматически старую подпись и не лечит компрометацию корневого ключа: в таком случае нужна отдельная доверенная доставка исправленного клиента и новый корень.

Закрытые ключи никогда не загружаются в GitHub Releases, Worker, приложение, сайт или отчёты.
